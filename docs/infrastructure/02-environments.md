# 02 · Environments

**Owner:** Jeff · **Status:** Draft v1 · 2 Oct 2026

## 1. Environment list

| Environment | Purpose | Where | Who deploys | Data | Uptime target |
|---|---|---|---|---|---|
| **local** | Day-to-day development | Developer laptop, Docker Compose | Developer | Seed data from `packages/test-utils` factories | — |
| **preview** | One short-lived copy per pull request (web + api) | `archova-dev` account, shared dev database with a schema per PR | CI on PR open; destroyed on merge/close | Seed data | Best effort |
| **dev** | Integration of `main`, always the latest code | `archova-dev` | CI on every merge to `main` | Seed data + synthetic tenants | Best effort, business hours |
| **staging** | Production rehearsal: same topology, smaller sizes | `archova-staging` | CI, automatically after dev passes smoke tests | Synthetic data generated at production-like volume. **Never** real customer data | 99% |
| **production** | Customers | `archova-prod` (cell 1) | CI, after manual approval | Real | 99.9% SLO |
| **loadtest** | Load and soak tests, chaos drills | `archova-loadtest`, built on demand from the same Terraform | Jeff | Synthetic, sized to the 100k target | Torn down after use |

There is no "UAT" environment. Pilot customers try new features in production behind feature flags, scoped to their org.

## 2. Local development

- `docker compose up` gives Postgres 16 (with pgvector), Valkey, MinIO (S3-compatible), OpenSearch (single node, optional profile), MailPit (catches email), and an OTel collector + Jaeger for local traces.
- Apps run natively with `pnpm dev` through Turborepo; only stores run in containers, so hot reload stays fast.
- LLM calls hit a local stub by default; a developer can opt into the dev Bedrock account with their SSO session.
- The same migration and seed commands run locally as in CI, so "works on my machine" means "works in CI".

## 3. What differs between environments

Everything is the same Terraform cell module with different variables. Topology is identical from staging up; only sizes and counts change.

| Setting | dev | staging | prod (cell 1, day one) |
|---|---|---|---|
| AZs | 2 | 3 | 3 |
| NAT gateways | 1 | 1 | 3 |
| `api` tasks (min/max) | 1/2 | 2/4 | 3/60 |
| `web` tasks | 1/2 | 2/4 | 3/30 |
| Aurora | Serverless v2 0.5–4 ACU, scales to near zero overnight | 1 writer + 1 reader `db.r7g.large` | 1 writer + 1 reader `db.r7g.large` (grows per [04](04-scaling-and-load.md)) |
| Valkey | single `cache.t4g.small` | primary + replica `cache.t4g.medium` | primary + replica `cache.t4g.medium`, two clusters (queue, cache); `r7g.large` from ~1k users |
| OpenSearch | single node or off | 3 small nodes | 3 data nodes (when introduced) |
| Backups | 1 day PITR | 7 days | 35 days PITR + AWS Backup plan (see [06](06-backup-and-dr.md)) |
| Spot capacity | Fargate Spot for everything | Spot for workers | On-demand for web/api/realtime; Spot allowed for retryable workers only |
| Scale to zero out of hours | Yes (weekday 7pm–7am AEST, weekends) | No | No |
| WAF | Managed rules, count mode | Block mode | Block mode |
| Domain | `*.dev.<domain>` | `*.staging.<domain>` | `app.<domain>`, `api.<domain>` |

(The product is Archova; `<domain>` stands in until the domain is registered.)

## 4. Data rules per environment

- **Production data never leaves production.** No copies to staging, dev or laptops. Support debugging uses read-only access to a prod read replica under audit (see [01 §2](01-cloud-setup.md#human-access)).
- **Staging data** is generated by a seeding job that creates ~10,000 synthetic orgs, 100,000 users and realistic volumes of RFIs, documents, photos and claims, so query plans and indexes behave like production.
- **Anonymised snapshots** of production for performance investigation are a later option and need Sam's sign-off: restore into an isolated account, run a masking job, then share.
- **Tenants in production** for internal use: a permanent "demo builder" org for sales and the hidden production synthetic tenant used by post-deploy and synthetic checks (X40, see [05 §5](05-observability.md#5-synthetic-checks)).

## 5. Secrets and configuration

| Kind | Where it lives | How apps get it |
|---|---|---|
| Secrets (DB passwords, API keys, signing keys) | Secrets Manager in each environment's account | ECS task definition `secrets` → environment variable at start-up |
| Non-secret config (URLs, limits) | Terraform outputs → SSM Parameter Store | Same mechanism |
| Feature flags, runtime tunables | AWS AppConfig | SDK polling with local cache; changes need no deploy |
| Build-time public values (web) | GitHub environment variables | Injected in the web build per environment |

Rules: no `.env` files committed; GitHub secret scanning and push protection on; every secret has an owner and a rotation period; database credentials rotate automatically.

## 6. Promotion path

```
PR ─► preview env ─► merge to main ─► dev (auto) ─► smoke tests ─► staging (auto) ─► E2E + perf smoke ─► approval ─► prod (blue/green, canary)
```

The same container image digest moves through every step; nothing is rebuilt between staging and prod. Details in [03](03-ci-cd.md).
