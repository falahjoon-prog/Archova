# @archova/mod-ai (Nova)

The `ai` module is the only door to AI models (X26). Design: [docs/ai/](../../docs/ai/) (Ari) and [ai-integration.md](../../docs/architecture/ai-integration.md) (Ava).

## Using Nova from a feature

Define the task's prompt in `@archova/ai-prompts` (`definePrompt`: id, version, feature, kind, tier, system prompt, input and output zod schemas, `render`, and `citations` if it cites), give it a credit price in `src/domain/credits.ts`, then call the gateway:

```ts
const run = await ai.runTask(ctx, myPrompt, input, { projectId, passages });
if (run.status === 'refused') {
  /* show "Nova couldn't answer this one" */
}
```

The gateway checks that Nova is on for the org, feature and caller, checks the monthly credit allowance (interactive work only), rate-limits per user, renders the prompt, routes the tier to a model, retries once and falls back a tier for interactive work, validates the output against the schema, drops citations that don't match a supplied passage, and logs every call in `ai.ai_requests` with credits and cost in `ai.ai_usage_ledger`. Output that changes a record goes into `ai.ai_suggestions`; the owning module applies it when a person accepts.

## Saving a suggestion

A draft a person accepts, edits or rejects is a pending `ai_suggestions` row, and `GET …/ai/suggestions` lists them. Every project member holds `ai.suggestions.read`, so that permission only opens the list. Who sees a row is declared per task in `src/domain/suggestion-audience.ts`, next to the permission that decides it:

- `creator`: only the person who asked can list or decide it (diary summaries, defect tags, RFI drafts, import mappings, quote readings). Someone else gets `ai.suggestion.not_found`, even an admin who holds the permission, because the draft was written from what only its asker may read or typed.
- `deciders`: the asker, and anyone on the project who holds the task's decide permission (drawing sheets, induction drafts). A subcontractor sees neither.

A task that isn't declared there is creator-only and can't be decided, so a new task starts closed. When you add one, declare it with the narrowest audience that works and add a case to the feature's integration test that lists and decides it as another project member.

## Ask Nova retrieval (F2)

`POST …/ai/index` brings a project's index up to date: every published document and drawing revision (from `documents.api.aiSources`) is read page by page, chunked (`src/domain/retrieval.ts`), embedded through the gateway (`embed`, 0 credits) and stored in `ai.ai_chunks` with its access scope (`drawings` or `folder:<id>`). Re-runs skip finished revisions, mark older revisions superseded, re-stamp moved documents and drop deleted ones. The ai-worker will run this on `documents.*` events once it exists.

`POST …/ai/ask` gets the caller's scopes from `documents.api.aiAccessScopes`. `qa.rewrite` (Fast tier) turns the question into up to 3 searches with shorthand spelled out, plus the document, sheet and clause references it names. Each search runs keyword (Postgres full-text) and vector (pgvector, exact) queries filtered to those scopes inside the query; everything is merged by reciprocal rank fusion. `qa.rerank` (Fast tier) scores the top 30, and the best 10 relevant passages go to `qa.answer`. Rewrite and re-rank are free and optional: if either fails, retrieval carries on without it. An answer without a valid citation becomes "not found" with the closest matches. Postgres needs the `vector` extension (`pgvector/pgvector:pg16` locally and in CI; RDS ships it).

Sent RFIs are indexed in the same run (`rfis.api.aiSources`: drafts and voided RFIs are left out). `src/domain/rfi-source.ts` turns an RFI into one page of text: its number, subject and status, the question, then each response marked "Official response" or "Comment (not the official response)", and a line saying so when there is no official response yet. Only the response the manager chose when closing the RFI is official, so a consultant's answer that is waiting to be closed reads as a comment and Ask will not present it as the decision (`qa.answer` v2 has the rule). The chunk's `revision_id` is a hash of that text, so an RFI with a new response, an edit or a new status indexes again and the old chunks and index entry are dropped; unchanged RFIs are skipped (`rfisIndexed` and `rfisUnchanged` in the report, separate from the document counts). RFI chunks have `source_type = rfi` and scope `rfis`, which `rfis.api.aiAccessScopes` gives only to builder staff with RFI read access, so a consultant or subcontractor never retrieves RFI text through Ask, even for an RFI addressed to them; they read their RFIs in the register. RFI drafting (F3) and induction drafting keep using the document scopes only. A citation to an RFI has `sourceType: rfi`, the RFI's `rfi_` id as both `sourceId` and `revisionId`, its status as `revision`, its subject as `title`, its number as `reference` and page 1.

Issued defects are indexed in the same run too (`defects.api.aiSources`: drafts and voided defects are left out, closed ones stay). `src/domain/defect-source.ts` turns a defect into one page of text: its number and title, then its status, priority, stage, trade, category, the company it is assigned to and the due date, its description, and the reasons and notes left on its history (a rejection, a dispute, a reassignment). `project-index.ts` indexes RFIs and defects through one `indexRecords` and `reconcileRecords`, each record a single page whose `revision_id` is a hash of that text, so a status change, a new assignee or a new note indexes again and the old chunks and index entry drop (`defectsIndexed` and `defectsUnchanged` in the report). Defect chunks have `source_type = defect` and scope `defects`, which `defects.api.aiAccessScopes` gives only to builder staff with defects read access: a subcontractor never retrieves defect text through Ask or search, even for a defect assigned to them (they work from their own list in the register). `qa.answer` v3 tells the model that only the status says where a defect stands: a subcontractor's "ready for review" is not the builder's sign-off. A citation to a defect has `sourceType: defect`, the defect's `dfx_` id as both `sourceId` and `revisionId`, its status as `revision`, its title as `title`, its `DEF-0042` number as `reference` and page 1.

Submitted and signed-off site diary days are indexed too (`diary.api.aiSources`: a day still being written is left out; it joins once the site manager submits it). `src/domain/diary-source.ts` turns a day into one page of text: its date and status, weather, site conditions, notes, the labour totals worked out in code, then labour, plant, deliveries, delays, stand-downs, visitors and each kind of event, each line spelled out as in the F4 summary (`lineText`). The summary and Ask share the line builder in the diary module (`summaryDay`). The entry's `version` does not change when a line is edited, so the chunk's `revision_id` is a hash of the text: an amended line, a late note or a sign-off indexes again and the old chunks and index entry drop (`diaryIndexed` and `diaryUnchanged` in the report). Diary chunks have `source_type = diary` and scope `diary`, which `diary.api.aiAccessScopes` gives only to organisation members who read the whole diary: a reader limited to their own company's labour (a subcontractor, even one who is an organisation member) and anyone outside the organisation, a superintendent included, hold none, so the notes, delays and other companies' labour never reach them through Ask or search. A citation to a diary day has `sourceType: diary`, the entry's `dia_` id as both `sourceId` and `revisionId`, its status as `revision`, "Site diary Monday 12 October 2026" as `title`, the date as `reference` and page 1. `qa.answer` v4 tells the model to report what the diary says with its date and never to say nothing happened on a day it has no passage for.

## Semantic search (F6)

`POST …/ai/search` is Ask's retrieval without the answer: the same indexed chunks, the same scopes (documents and drawings from `documents.api.aiAccessScopes`, plus RFIs for builder staff from `rfis.api.aiAccessScopes`, built once in `createAiModule` and shared with Ask) and the same permission (`ai.ask.use`). The scope filter is part of each SQL query under RLS, so a hit is always something the caller can open from its link, and a private folder, another org's passage or an RFI a consultant isn't staff for is never returned. The only model call is the embedding of the query (`embed.query`, 0 credits, still behind the org and feature switches, so Nova off means search off too). Each search pays for an embedding, so the gateway counts it against a per-user limit of 120 in ten minutes (`queryRateLimit`, looser than the 30 interactive runs, in the same Redis window scheme); the 121st is `429 rate_limited`.

`searchChunks` runs keyword and vector search and merges them by reciprocal rank fusion, as for Ask. The service asks for three times the wanted number of passages, keeps the best-ranked passage of each page of each revision (`onePerPage`: a long page is several chunks and should be one result) and cuts the list to `limit` (default 10, at most 20). Each result is a `NovaSource` (the same link fields a citation has) plus a `snippet` (`src/domain/search-results.ts`): the passage itself when short, otherwise about 240 characters around the first query word it contains, cut on word boundaries and marked with ellipses, or its start when it contains none (a passage found by meaning alone).

The closest passages are returned even when none is close, because there is no relevance cut-off yet: the vectors have no calibrated distance until the real embedding model's retrieval eval exists (ai/06). An empty list therefore means nothing is indexed that the caller can see. A blank query returns nothing without embedding it. Other sources (diary, defects, correspondence in ai/01 F6) join when those modules supply `aiSources`.

## Scanned pages (OCR)

A PDF page with no text layer is treated as a scan: `src/infra/pdf.ts` finds the image covering most of the page, `src/infra/raster.ts` turns it into a greyscale PNG (at most 5,000 px a side and under Textract's 10 MB limit, in plain TypeScript with no native canvas), and the gateway's `ocr` sends it to Textract `DetectDocumentText` in the provider's Australian region. OCR is background work: 0 credits, never stopped by the allowance, logged per page in `ai_requests` (tier `ocr`). Ask Nova indexing uses the OCR text like a text layer; the drawing register maps OCR lines back to page positions, picks the title block region and checks every field against it, and marks those suggestions `scanned: true`. Lines under 40% confidence are dropped. Pipeline version 2 re-indexes every revision once, so scans indexed before OCR existed are picked up.

## Diary summaries (F4)

`api.summariseDiaryDay(ctx, projectId, day)` takes one day from `diary.api.dayForSummary` (only the lines the caller may see) and drafts a short daily report with `diary.summary` (Standard tier, 0.5 credit, feature `diary_summary`). `src/domain/diary-summary.ts` numbers the lines as facts (`l1`, `l2` ...), adds the weather (`w`) and labour totals computed in code (`t`), and checks the output: a sentence that cites no supplied fact, or states a number its facts don't contain, is dropped; delay and stand-down lines no sentence mentions are listed in `unmentionedDelays`; "possible delay" is always raised when the day has a delay or stand-down line, with the cause the site recorded. The draft is a pending `ai_suggestions` row (target `diary_entry`) that the person who asked accepts, edits or rejects; it is reused for that person until the day's lines, weather or entry change (the cache key is the asker plus `dayFingerprint`, because the entry's own version doesn't change when a line is added). Like defect tags, the row is creator-only (see Saving a suggestion): the draft names the lines its asker may read (a company sees only its own), so nobody else can list or decide it, and someone else asking the same day gets, and pays for, a draft of their own. The route is `POST …/diary/{date}/nova-summary` (needs `diary.entries.read`): `summariseDate` reads the day through `diary.api.dayForSummary` as the caller, so a subcontractor's summary is written from their own company's lines only, and a missing day or no access is `diary.not_found`. An empty day is 422 `ai.diary.nothing_to_summarise`.

## Weekly diary summaries (F4)

`api.summariseDiaryWeek(ctx, projectId, weekStart)` (route `POST …/diary/weeks/{weekStart}/nova-summary`, needs `diary.entries.read`) drafts a short report for the client or head office with `diary.weekly` (Standard, 1 credit, feature `diary_summary`). `weekStart` must be a Monday (422 otherwise). The week is read one day at a time through `diary.api.dayForSummary` as the caller, so a company's summary is written from its own lines only; a week with no entry is `diary.not_found` and one whose entries are empty is 422 `ai.diary.nothing_to_summarise`. `src/domain/diary-weekly.ts` turns the days into facts with the same wording as the daily summary (`d3l2` is line 2 of Wednesday, `d3w` its weather, `d3t` its labour totals) and adds `wt`, the week's totals calculated in code: labour hours, the busiest day, delay hours by cause and stand-down lines. The model is told never to add numbers up. A day with more than 40 lines keeps its delays, stand-downs and events first and drops routine lines (`truncated`); the totals still count every line. Sentences go through the daily summary's checks (`reviewSentences`): one that cites no supplied fact, or states a number its facts (or the week's dates) don't contain, is dropped; delay and stand-down lines no sentence mentions are listed in `unmentionedDelays`. Each source carries the `date` of its day. The payload also holds `delayHours` (total and by cause, from code). The draft is a pending, creator-only `ai_suggestions` row (task `diary.weekly`, target the project, cached per person and week content), so the diary is never written to; there is no weekly report record yet, so accepting it just records that the person used it.

## RFI drafts (F3)

`api.draftRfi` (route `POST …/ai/rfi-drafts`, needs `rfis.rfis.create`) turns a note typed on site into an RFI subject and question with prompt `rfi.draft` (Standard, 1 credit). The note is embedded and searched once under the caller's access scopes; the draft cites the passages it relies on, and the gateway drops citations that don't match. Numbers in the draft found in neither the note nor a cited passage (title included) come back in `unsupportedNumbers` for the form to highlight. Similar RFIs come from `rfis.api.findSimilar` (full-text, only RFIs the caller can see, no drafts or voided ones), and suggested assignees are whoever was asked those, most often first. Nova sends nothing: the draft fills the RFI form and the person sends it. Each draft is kept as a pending `ai_suggestions` row (task `rfi.draft`, target the project; payload holds the subject, question, discipline, the cited sheets and clauses without quotes, similar RFI ids, suggested assignee ids and the pin), and the response carries its `suggestionId`. Like defect tags, the row is private: only the person who asked can list or decide it. The apps pass `suggestionId` as `aiSuggestionId` on `POST …/rfis`, which stores it on the RFI and puts it on `rfis.rfi.created.v1`, then decide the suggestion as `accepted`, `edited` or `rejected`; the pilot bars "sent with light or no edits" and "correct drawing reference" (ai/01 §4) are read from that decision and the RFI's final pin and references. From a markup: the body can also carry `markup: {drawingRevisionId, markupId}` (needs `documents.drawings.read`, and the caller must be able to see that markup, so a private one is `markup.not_found` to anyone else). Code reads the sheet's text (OCR for scans, as revision compare does), keeps the words written on the markup (`labels`) and the sheet lines inside the marked area plus a margin (`nearby`, nearest first, at most 25), and sends them with the note; the note may be empty when the markup has text. The question names the sheet and revision, `nearby` is untrusted sheet content like any passage, and the response's `drawing` gives the sheet and the `pin` (the pin shape, else the middle of the markup) for the RFI form. From a site photo: the body can also carry `photo: {fileId}`, a PNG, JPEG or WebP already uploaded to this project (the file read applies the caller's access; another project's file, a non-image or one over 3 MB is a 422). The photo goes to the model as an image (prompt `rfi.draft` v3) and the draft says what it shows; a photo shows a condition, not a place, so `location` is listed in `gaps` unless the note gives one, and a number read off the photo that isn't in the note is listed in `unsupportedNumbers`. A photo alone is enough to draft from: with no text there is nothing to search, so no passages are sent and no embedding run is made. Marks and clouds on drawings come with the vision pass.

## Defect photo tagging (F5)

`api.tagDefect` (route `POST …/ai/defect-tags`, needs `defects.defects.create`) turns a defect photo into a suggested title, description, trade, kind of defect and priority with prompt `defect.tag` (Fast tier, vision, 0.1 credit, feature `defect_tagging`). The body is `photo {fileId}` (a PNG, JPEG or WebP already uploaded to the project, up to 3 MB, read the same way as an RFI photo), an optional `note`, and an optional `pin {drawingRevisionId, x, y}`. With a pin, code reads the sheet's text (OCR for scans) and sends the lines near the pin, so the title can name the room or grid line exactly as the drawing prints it; without one no place is named and `location` is listed in `gaps`. The model picks from fixed lists (25 trades and 15 kinds of defect in `@archova/ai-prompts`); the response gives them as the labels a defect stores in `trade` and `category`, with up to two `alternativeTrades`. Priority is `medium` unless the photo shows otherwise, and `critical` is for a hazard to people that is visible now. Numbers in the title or description found in neither the note nor the sheet text come back in `unsupportedNumbers`.

Two things come from code, not the model. `suggestedCompanies` are companies on the project whose listed trades match the suggested trade (then an alternative), from `platform.api.projectCompaniesWithTrades`; Nova never picks the assignee. `duplicates` are live defects the caller can see within 6% of the sheet from the pin (`defects.api.openNear`, nearest first, `sameTrade` marked), so the person can see it is already logged. Nova raises no defect: the suggestion fills the defect form and the person saves it. Each tag is kept as a pending `ai_suggestions` row (task `defect.tag`, target the photo) whose payload holds the proposed tags, the offered company ids and the duplicate ids, and the response carries its `suggestionId`. The row is private: only the person who asked can list it (`GET …/ai/suggestions`) or decide it, because the photo and note are theirs until they raise the defect. The web and mobile apps pass `suggestionId` as `aiSuggestionId` on `POST …/defects`, which sets `source: ai_suggested`, stores the link and puts it on `defects.defect.created.v1`; then they decide the suggestion as `accepted` (used as given), `edited` (the person changed Nova's tags, nothing to send) or `rejected` (nothing raised). `ai.suggestion.decided.v1` plus the defect's final trade and assignee are what the suggested-assignee accept rate (ai/01 §4) is read from. The eval suite scores the safety bars on synthetic notes; trade accuracy against the ai/01 §4 bars (top-1 85%, top-3 95%) needs labelled photos and a real model.

## Import mapping (F31)

`api.suggestImportMapping` (route `POST …/ai/import-mappings`, needs `ai.import_mapping.suggest`, held by project admins until the importer has a tool of its own) suggests which Archova field each column of an import file fills, with prompt `import.mapping` (Fast tier, 0.25 credit per file, feature `import_mapping`). The task id is `import.mapping`, not the `import.mapping.suggest` the integrations doc names, because task ids are `<area>.<task>`; the permission and the suggestion row keep that name. The import screen parses the file and sends, per column, its header, up to five values and, for a column with at most 30 distinct values (status, priority), those values; nothing else leaves the building, and the stored suggestion keeps none of them. `entity` picks the catalog in `@archova/ai-prompts` (`IMPORT_FIELDS`: `rfi`, `defect`, `drawing_register`, `company`), which lists each field with its kind, whether it is required, the words other tools use for it, and for status-like fields the values Archova stores. Whoever builds an importer adds its fields there.

The model answers per column with a field key (or null) and a confidence, and for columns that fill a field with fixed values, what each file value means. `src/domain/import-mapping.ts` then keeps only fields that exist, gives each field to one column (surest first, then the header that names it, then the earlier column), withdraws a suggestion whose values don't look like that kind of field (a date field whose column holds names; fewer than half fit) or caps its confidence (fewer than 80% fit), fills `examples` from the file, gives every distinct value in a status-like column a row (the model's meaning if it is one of the field's values, else the catalog's words, else null for the person to choose), and lists required fields no column fills in `missingRequired`. The response also carries the field catalog so the screen can offer it when the person changes a suggestion. Header and value text is untrusted data. The suggestion is a pending `ai_suggestions` row (target the project), private to the person who asked like other drafts built from their files; the screen passes its `suggestionId` when the import job starts and decides it `accepted`, `edited` or `rejected`, so the ai/11 bar (at least 90% of columns right on 30 exports) can be read from suggestion against final mapping.

## Quote reading (F22)

`api.readQuote` (route `POST …/ai/quote-readings`, needs `estimating.quotes.review`) reads a subcontractor's PDF quote against the tender package it answers, with prompt `quote.read` (Standard tier, 1.5 credits, feature `quote_reading`). The body is `{packageId, fileId}`; the file must be a PDF already uploaded to the same project, up to 30 MB. Code reads the text of each page as printed rows (columns split by two spaces; OCR for a scanned page, up to 10 pages, 0 credits), up to 30 pages, 6,000 characters a page and 60,000 in all; anything cut is listed in `skippedPages` and `truncated`. The package comes from `estimating.api.scopeForQuoteReading`, so only builder staff can read quotes for a package that is out to tender or later; the model gets the trade and the scope lines (key, description, quantity, unit), never ids or company names.

The model returns the quote's reference, `validUntil`, whether prices include GST, the printed total, priced lines (with `provisional` for provisional and prime cost sums), exclusions and qualifications, each with the page and the words it came from. `src/domain/quote-read.ts` checks all of it against the page text. A source is kept only if its words are found on the page named (or another page); a line whose amount is not printed on its page is kept with `amount_not_on_page`, one whose words are on no page with `source_not_found`; a printed total that is on no page is dropped (`stated_total_not_on_page`); scope keys the package does not have become null; lines with an amount code can't read are dropped and counted in `dropped`. Discounts, credits and bracketed amounts are never lines: they become qualifications ("Discount or credit: …") and are netted off in `totalCheck`, which says `matches`, `differs` (with the signed `difference`) or `not_stated` by comparing the lines, less discounts, with the printed total ex GST. `prices_include_gst` warns when the quote says its amounts include GST, because the lines are then not comparable as they stand. Quote text is untrusted: the prompt treats it as data and the eval suite has an injection case.

The reading is a pending `ai_suggestions` row (task `quote.read`, target the tender package), private to the person who asked like other drafts built from their files, and the response carries its `suggestionId`. The estimator checks the lines against the PDF (each line links to its page) and saves the quote with `aiSuggestionId` on `POST …/tender-packages/{id}/quotes`, which marks it `ai_extracted`; then the screen decides the suggestion `accepted`, `edited` (the estimator corrected lines) or `rejected`. Nova creates no quote and confirms none; the estimator does that.

## Drawing revision compare (F21)

`api.compareDrawingRevision` (route `POST …/ai/drawing-revisions/{id}/changes`, needs `documents.drawings.read`) says what changed on a drawing revision since the one it superseded. Code reads the text of both sheets (OCR for scans), groups it into lines with positions and diffs them: lines added, removed, or changed in place (similar wording nearby, or an edit in the same spot). Unchanged text that moved isn't a change. Prompt `drawing.compare` (Standard, 0.5 credit, feature `drawing_compare`) words the changes; items that cite no real change or add a number are dropped, and changes no item covers come back as `unexplainedChangeIds`. The result is stored once per revision pair in `ai_drawing_compares` and shared. No text changes means no model call. Open RFIs pinned to either revision come from `rfis.api.openOnDrawing` per request, marked `nearChange` when a change sits within 10% of the sheet from the pin. Where a page renderer is installed the linework is compared too (next section); the response's `visual` is null where it isn't.

### Linework: the vision pass (F21)

Text only misses most of a revision (walls moved, a door added, a pipe re-routed), so a second pass compares the pictures.

- `domain/visual-diff.ts` (pure, no IO) takes two greyscale renders of the same sheet at the same scale and finds where ink was added or removed. It lines the old sheet up with the new one (projection profiles, up to 16 px, only when clearly better so a real change doesn't drag the sheet), ignores line-width wobble and anti-aliasing (a pixel only counts when the other sheet has no ink within 2 px), counts changed ink per 32 px cell, joins cells with at most one empty cell between them, and keeps the 12 biggest regions (`truncated` says more existed). Two sheets of different shape, a blank render, or a sheet where more than a quarter of the cells changed (redrawn, not revised) come back `reliable: false` with a `reason` and no regions, so a failed render can't read as "everything changed".
- `domain/visual-compare.ts` pairs each region with the sheet text near it and the text changes inside it (`changeIds`, from the text compare), cuts one picture of the old and new sheet side by side, and reviews what Nova says. Every region found is returned in order. A description is kept only if it names a region we sent, isn't a repeat, and every whole number in it appears in the text near that region; otherwise the region gets a plain sentence from its kind (`described: false`).
- Prompt `drawing.compare_visual` (Fast tier with vision, 0.5 credit, feature `drawing_compare`) describes up to 12 regions in one call (one image each, 12 stays under the 20-image limit) and returns, per region, a sentence, what kind of thing changed and whether a revision cloud marks it. The cloud answer is what the model saw on the new sheet; code can't verify it, so the screen should say "Nova saw/didn't see a cloud". Nova never finds a region and can't hide one.
- `application/visual-compare.ts` `compareVisually(gateway, ctx, {rasters, text, ...})` runs it: no regions or an unreliable pair means no model call and no charge; a refused run still returns the regions with `complete: false` so callers don't store it.

`compareDrawingRevision` runs it when the module is given a `rasterizePage(file, pageIndex)` dep (whole page as greyscale, longer side 2,000 px) and returns it as `visual`: `{runId, reliable, reason, truncated, regions[]}`, each region with its box on the new sheet (0..1 from the top left), `kind`, `summary`, `described`, `what`, `cloud` and `changeIds` (the text changes in or next to it, ids from `changes`). The result is stored once per revision pair and visual prompt version in `ai_drawing_visual_compares` (separate from the text half, which is worded by a different step) and shared. A step that can't run (the page won't render, the allowance is used, Nova is busy) returns `reliable: false` with `reason` `render_failed`, `allowance_used` or `unavailable`, is not stored, and never holds back the text half; opening the compare again retries.

There is no renderer in the API image: pdf.js needs a native canvas (`@napi-rs/canvas`), which Jeff approved for an `ai-worker` image only. So `visual` is null in the API today, and the next slice is the worker that renders pages and calls the same service. Tests and a developer's machine pass a stub or a real rasterizer through `buildApp({ aiRasterizePage })`.

## Induction drafts (F33)

`POST …/ai/induction-drafts` searches the caller's visible documents once per required induction section (compliance/04 §2), then `induction.draft` writes slides, a script and a quiz. `src/domain/induction.ts` checks the draft before it is stored: items whose citation doesn't quote a passage, whose numbers aren't in their source, or that use a banned word are removed and listed in `warnings`; empty sections become `missing`; critical quiz flags are forced. The declaration and fixed safety sentences come from `INDUCTION_FIXED_TEXT`, not the model. The draft is a pending `ai_suggestions` row; `workforce` creates the induction version when the builder accepts (docs/ai/12).

## Induction Q&A (I3)

`api.indexInductionVersion` chunks a published induction version's slides and script (one page per slide) into `ai_chunks` with `source_type = induction` and scope `induction:<version id>`. `api.askInduction` searches that scope only and runs `induction.ask` (0.25 credit, feature `inductions`). An answer without a valid citation, or a question with nothing retrieved, returns `INDUCTION_ASK_SUPERVISOR` ("ask your supervisor or the site office"). Ask Nova never retrieves induction chunks, because `documents` never grants an `induction:` scope, and the project indexer only reconciles `document` and `drawing` chunks. These are module API calls with no route: `workforce` calls them on publish, and from the worker's route after the X45 access-link check.

## Induction translation (I4)

`api.translateInduction(ctx, version, language)` translates an approved induction version slide by slide and question by question (`translation.translate`, Standard tier, 0.25 credit per unit). Numbers, phone numbers, times, units, codes and kept terms (`src/domain/translation.ts`) go to the model as placeholders and are put back by code; a dropped or extra placeholder fails the unit. `translation.check` (Fast tier, free) back-translates each unit and judges whether the meaning held. A unit that fails stays in English with the language's fixed "ask your supervisor" note. Results are cached in `ai_translations` per version, source hash, language, glossary version and prompt version, with a `translationHash` for the completion record. Only languages in `TRANSLATION_LANGUAGES` with `enabled` and reviewed `labels` are offered (`api.translationLanguages`), and none is enabled until its glossary and labels are reviewed and its eval passes against Bedrock AU (compliance/03 §6).

## Providers

| `API_AI_PROVIDER` | Use                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fake` (default)  | Tests and local development. No network or credentials; tests script replies per task.                                                                                                                                                                                                                                                                                                                                |
| `bedrock`         | Deployed environments. Needs `API_AI_REGION` in Australia, `API_AI_MODEL_FAST/STANDARD/ADVANCED` and `API_AI_MODEL_EMBEDDING` (default Titan Text Embeddings V2). Only in-region model ids or `au.` inference profiles are accepted (X25); `apac.`, `us.`, `global.` and the rest are refused. OCR uses Textract in the same region (`textract:DetectDocumentText`; `API_AI_TEXTRACT_ENDPOINT` for its VPC endpoint). |

Vendor SDKs may be imported only in `src/infra/providers/` (`pnpm check:boundaries`).

## Evals

```sh
pnpm --filter @archova/mod-ai eval                                 # every suite, fake provider (CI)
pnpm --filter @archova/mod-ai eval --task qa.answer --provider bedrock --sample 50 --out report.md
```

Each suite (`src/eval/suites.ts`) is a task's prompt, its golden set (synthetic or public documents only until a pilot gives written consent), a scorer and the acceptance bars from docs/ai/01 §4. The run exits 1 when any metric is below its bar; safety metrics (tenant canaries, restricted sources) have a bar of 100%. The fake provider runs the prompt, schema, citation check and scorers on every change; real scores need `--provider bedrock` with `AI_EVAL_MODEL_*` set.
